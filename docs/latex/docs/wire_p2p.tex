\hypertarget{satspath-p2p-wire-transport-v1}{%
\section{SatsPath P2P Wire Transport
v1}\label{satspath-p2p-wire-transport-v1}}

Pear/Holepunch is an optional transport for SatsPath protocol objects.
It is not the SatsPath protocol.

This document defines how a P2P transport carries signed profiles and
resolver messages while preserving the protocol rules in
\href{./protocol.md}{protocol.md}.

\hypertarget{transport-role}{%
\subsection{Transport Role}\label{transport-role}}

P2P transport can be used to:

\begin{itemize}
\tightlist
\item
  Announce that a peer has a signed payment profile for an identifier.
\item
  Request a signed profile for an identifier.
\item
  Return a \texttt{SignedPaymentProfile}.
\item
  Exchange resolver diagnostics.
\end{itemize}

P2P transport MUST NOT:

\begin{itemize}
\tightlist
\item
  Replace profile signatures.
\item
  Carry wallet seeds or spending keys.
\item
  Authorize payments by itself.
\item
  Treat peer connectivity as proof of profile ownership.
\end{itemize}

\hypertarget{topic-derivation}{%
\subsection{Topic Derivation}\label{topic-derivation}}

The reference Holepunch SDK uses a topic derived from a canonicalized
alias:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{topic = SHA256("satspath:p2p:v1:" + canonical\_identifier)}
\end{Highlighting}
\end{Shaded}

The topic hides the raw alias from casual discovery but is not a privacy
guarantee against dictionary attacks. Clients SHOULD avoid announcing
sensitive identifiers unless that tradeoff is acceptable.

\hypertarget{message-envelope}{%
\subsection{Message Envelope}\label{message-envelope}}

All P2P messages SHOULD use a versioned envelope:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{\{}
  \DataTypeTok{"protocol"}\FunctionTok{:} \StringTok{"satspath"}\FunctionTok{,}
  \DataTypeTok{"version"}\FunctionTok{:} \DecValTok{1}\FunctionTok{,}
  \DataTypeTok{"type"}\FunctionTok{:} \StringTok{"profile\_response"}\FunctionTok{,}
  \DataTypeTok{"request\_id"}\FunctionTok{:} \StringTok{"01J..."}\FunctionTok{,}
  \DataTypeTok{"body"}\FunctionTok{:} \FunctionTok{\{\}}
\FunctionTok{\}}
\end{Highlighting}
\end{Shaded}

Fields:

\begin{itemize}
\tightlist
\item
  \texttt{protocol}: MUST be \texttt{satspath}.
\item
  \texttt{version}: MUST be \texttt{1} for this wire version.
\item
  \texttt{type}: Message type.
\item
  \texttt{request\_id}: Optional caller-generated correlation ID.
\item
  \texttt{body}: Type-specific payload.
\end{itemize}

Implementations MAY carry raw \texttt{SignedPaymentProfile} objects for
compatibility, but versioned envelopes are preferred for forward
compatibility.

\hypertarget{verification-rules}{%
\subsection{Verification Rules}\label{verification-rules}}

On receipt of a P2P profile response, a client MUST:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Decode JSON.
\item
  Confirm \texttt{protocol\ ==\ "satspath"} and \texttt{version\ ==\ 1}
  if using an envelope.
\item
  Decode \texttt{SignedPaymentProfile}.
\item
  Verify the profile signature.
\item
  Check expiry.
\item
  Reject private material.
\item
  Optionally persist the verified profile into the local registry.
\end{enumerate}

Peer identity, DHT topic, or transport connection state MUST NOT bypass
these checks.

\hypertarget{connection-state}{%
\subsection{Connection State}\label{connection-state}}

Implementations SHOULD expose connection diagnostics separately from
protocol verification:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{\{}
  \DataTypeTok{"kind"}\FunctionTok{:} \StringTok{"p2p\_bridge"}\FunctionTok{,}
  \DataTypeTok{"status"}\FunctionTok{:} \StringTok{"started"}\FunctionTok{,}
  \DataTypeTok{"active"}\FunctionTok{:} \KeywordTok{true}\FunctionTok{,}
  \DataTypeTok{"detail"}\FunctionTok{:} \StringTok{"pid:1234"}
\FunctionTok{\}}
\end{Highlighting}
\end{Shaded}

Connection state can explain discovery failures, but it does not prove
payment safety.

\hypertarget{reference-implementation}{%
\subsection{Reference Implementation}\label{reference-implementation}}

The reference P2P transport lives in:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{sdk/satspath{-}p2p/}
\end{Highlighting}
\end{Shaded}

The daemon can start an optional bridge:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{satspathd {-}{-}p2p}
\end{Highlighting}
\end{Shaded}

The bridge publishes the local signed profile over the P2P transport.
The same profile can also be served over HTTPS, imported from a file, or
discovered through other resolvers.

\hypertarget{compatibility}{%
\subsection{Compatibility}\label{compatibility}}

Version 1 receivers SHOULD ignore unknown envelope fields. Version 1
receivers MUST reject unknown required message semantics if a future
message declares them.

Future wire versions may change message types or add encryption, but
must preserve the core protocol invariant: profiles are verified as
SatsPath signed profiles before routing.
