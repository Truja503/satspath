\hypertarget{satspath-protocol-v1}{%
\section{SatsPath Protocol v1}\label{satspath-protocol-v1}}

SatsPath is a payment discovery and routing protocol for Bitcoin rails.
It defines signed payment profiles, verification rules, resolver
semantics, and quote responses for Lightning, on-chain, and Ark receive
pointers.

SatsPath is not a wallet, not a Bitcoin node, and not a
transport-specific peer-to-peer system. Pear/Holepunch is one possible
transport for moving SatsPath protocol objects between machines; it is
not the protocol itself.

\hypertarget{scope}{%
\subsection{Scope}\label{scope}}

SatsPath v1 specifies:

\begin{itemize}
\tightlist
\item
  Human-readable recipient identifiers.
\item
  Signed payment profiles.
\item
  Public receive pointers for Lightning, on-chain Bitcoin, and Ark.
\item
  Resolver semantics for locating signed profiles.
\item
  Verification rules before routing.
\item
  Quote response states for wallet and UI clients.
\item
  Transport-neutral behavior, including how optional P2P transports
  carry protocol objects.
\end{itemize}

SatsPath v1 does not specify:

\begin{itemize}
\tightlist
\item
  Custody of funds.
\item
  Wallet seed or spending-key storage.
\item
  Mainnet transaction signing.
\item
  Mainnet transaction broadcast.
\item
  Lightning node operation.
\item
  Ark server operation.
\end{itemize}

Payment execution belongs to the underlying wallet or rail. SatsPath
discovers and validates where a payment can be sent, then returns public
payment instructions.

\hypertarget{terminology}{%
\subsection{Terminology}\label{terminology}}

\begin{description}
\tightlist
\item[\texttt{Identifier}]
A human-readable name for a receiver, normally \texttt{user@domain}.
\item[\texttt{PaymentProfile}]
Public profile data containing a receiver alias, protocol identity
public key, supported payment methods, timestamps, and optional
method-verification records.
\item[\texttt{SignedPaymentProfile}]
A \texttt{PaymentProfile} plus a secp256k1 Schnorr signature made by the
profile identity key.
\item[\texttt{PaymentMethod}]
One public receive pointer. v1 methods are \texttt{Lightning},
\texttt{Onchain}, and \texttt{Ark}.
\item[\texttt{Resolver}]
A component that maps an identifier to a \texttt{SignedPaymentProfile}.
\item[\texttt{QuoteResponse}]
The protocol-level response returned after resolution, signature
verification, expiry checks, route selection, and payment-payload
construction.
\item[\texttt{Transport}]
A way to carry SatsPath objects. Examples include local files, HTTPS,
DNS/BIP-353, Nostr, and Pear/Holepunch.
\end{description}

\hypertarget{identifiers}{%
\subsection{Identifiers}\label{identifiers}}

The canonical identifier format is:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{\textless{}local{-}part\textgreater{}@\textless{}domain\textgreater{}}
\end{Highlighting}
\end{Shaded}

Resolvers MUST treat identifiers as case-insensitive for lookup
normalization unless the transport defines stricter semantics.
Implementations SHOULD trim leading and trailing whitespace before
lookup.

An identifier by itself is not an ownership proof. A profile signature
proves control of the SatsPath protocol identity key embedded in the
profile. DNSSEC, HTTPS well-known, Nostr/NIP-05, or a platform verifier
may add evidence that the identifier was published or approved by the
relevant domain/account, but plain email syntax alone MUST be treated as
\texttt{identifier-only}.

Examples:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{alice@example.com}
\NormalTok{rodrigo@satspath.dev}
\NormalTok{shop@merchant.example}
\end{Highlighting}
\end{Shaded}

BIP-353 names MAY be represented with a leading Bitcoin sign:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{₿alice@example.com}
\end{Highlighting}
\end{Shaded}

The leading sign selects DNS payment-instruction resolution behavior; it
does not change the receiver identity once normalized.

\hypertarget{signing-rule}{%
\subsubsection{Signing Rule}\label{signing-rule}}

The signature is computed over a domain-separated SHA-256 digest of the
canonical JSON serialization of \texttt{profile}.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{message = SHA256(UTF8("SatsPathProfileV1") || canonical\_json\_utf8(profile))}
\NormalTok{signature = secp256k1\_schnorr\_sign(identity\_secret\_key, message)}
\end{Highlighting}
\end{Shaded}

Implementations MUST keep serialization stable for the profile shape
they sign. Implementations MUST NOT sign or transmit wallet seeds,
xprv/tprv material, mnemonics, Lightning macaroons, Ark claim keys,
refund keys, or other private spending material.

\hypertarget{verification-rule}{%
\subsubsection{Verification Rule}\label{verification-rule}}

Before using any profile for routing, an implementation MUST:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Parse \texttt{identity\_pubkey} from hex as exactly a 33-byte
  compressed secp256k1 public key (\texttt{02}/\texttt{03} prefix).
\item
  Serialize with RFC 8259 JSON semantics, recursively lexicographically
  sorted object keys, UTF-8, and no insignificant whitespace.
\item
  Recompute
  \texttt{SHA256(UTF8("SatsPathProfileV1")\ \textbar{}\textbar{}\ canonical\_json\_utf8(profile))}.
\item
  Decode \texttt{signature} as exactly 64 bytes of hex and verify
  secp256k1 Schnorr against the x-only projection of the compressed key.
  DER ECDSA MUST be rejected.
\item
  Reject the profile if \texttt{expires\_at} is present and in the past.
\item
  Reject private material if any private-key-like content is detected in
  public fields.
\end{enumerate}

Profile schema/signature version 1 is selected by
\texttt{SatsPathProfileV1}; an incompatible future profile requires a
new domain.

\hypertarget{key-rotation-v1}{%
\subsubsection{Key Rotation V1}\label{key-rotation-v1}}

The old key authorizes and the new key separately accepts these
newline-delimited UTF-8 statements (no trailing newline):

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{SatsPathKeyRotationAuthorizationV1}
\NormalTok{identifier\_hash}
\NormalTok{old\_pubkey}
\NormalTok{new\_pubkey}
\NormalTok{previous\_event\_hash}
\NormalTok{sequence}
\NormalTok{rotated\_at}
\end{Highlighting}
\end{Shaded}

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{SatsPathKeyRotationAcceptanceV1}
\NormalTok{identifier\_hash}
\NormalTok{old\_pubkey}
\NormalTok{new\_pubkey}
\NormalTok{previous\_event\_hash}
\NormalTok{sequence}
\NormalTok{rotated\_at}
\end{Highlighting}
\end{Shaded}

Each complete statement is SHA-256 hashed and signed as a 64-byte
secp256k1 Schnorr signature. \texttt{identifier\_hash} is
\texttt{SHA256(UTF8(canonical\_identifier))}.

If signature verification fails, the protocol result MUST be
\texttt{invalid\_signature}.

If the profile is expired or unusable, the protocol result MUST be
\texttt{no\_route}.

\hypertarget{resolver-semantics}{%
\subsection{Resolver Semantics}\label{resolver-semantics}}

A resolver maps an identifier to a \texttt{SignedPaymentProfile}.

Resolver results are:

\begin{itemize}
\tightlist
\item
  \texttt{found}: a signed profile was found and returned.
\item
  \texttt{not\_found}: no signed profile exists for this identifier in
  that resolver.
\item
  \texttt{unavailable}: resolver transport failed or timed out.
\item
  \texttt{invalid}: resolver returned malformed or unsafe data.
\end{itemize}

A resolver chain MUST continue past \texttt{not\_found} and transient
\texttt{unavailable} results. A resolver chain MUST stop on a
successfully verified profile. A resolver chain MAY stop on
\texttt{invalid} when the invalid data is authoritative for that
identifier.

Resolver behavior is specified in \href{./resolvers.md}{resolvers.md}.

\hypertarget{quote-response-contract}{%
\subsection{Quote Response Contract}\label{quote-response-contract}}

SatsPath Mainnet Preview is a public-data-only protocol mode that
operates strictly in the first three phases of a payment lifecycle:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Resolve}: Fetch the signed profile for the identifier.
\item
  \textbf{Route}: Check signatures, expiry, ownership, and select the
  best rail.
\item
  \textbf{Invoice Presentation}: Fetch LNURL/BOLT11 data, format BIP-21
  or Ark URIs, and display the payment pointer or QR.
\item
  \textbf{Execution}: \textbf{(Out of scope for Mainnet Preview)} The
  user scans the QR and pays using their own wallet.
\end{enumerate}

The protocol quote response is serialized as a JSON object tagged by
\texttt{status}.

The payload preview formats are:

\begin{itemize}
\tightlist
\item
  \texttt{lightning:\textless{}address\textgreater{}} for Lightning
  Address preview,
\item
  \texttt{lnurl:\textless{}url\textgreater{}} for LNURL preview,
\item
  a BOLT11 invoice string only when explicitly fetched by the caller,
\item
  \texttt{bitcoin:\textless{}address\textgreater{}?amount=\textless{}btc\textgreater{}}
  for on-chain mainnet preview,
\item
  \texttt{satspath:ark?...\&network=mainnet} for Ark public pointer
  preview.
\end{itemize}

It must not:

\begin{itemize}
\tightlist
\item
  sign transactions,
\item
  broadcast transactions,
\item
  execute Lightning payments,
\item
  execute Ark transfers,
\item
  execute swaps,
\item
  handle seeds, xprv/tprv, macaroons, certs, API secrets, claim keys,
  refund keys, or wallet private keys.
\end{itemize}

Mainnet execution (Phase 4 automation) is not part of v1 prototype
behavior and no execution flag exists for mainnet.

\hypertarget{experimental-swap-engine-execution-phase}{%
\subsection{Experimental Swap Engine (Execution
Phase)}\label{experimental-swap-engine-execution-phase}}

Execution automation (such as submarine swaps, reverse swaps, or Ark
VTXO transfers) is built into an experimental engine that is
\textbf{strictly testnet-only}. This engine handles Phase 4, but is
disabled by default and sandboxed away from mainnet to prevent any risk
to real funds.

\end{Shaded}

Clients MUST NOT offer payment execution for
\texttt{invalid\_signature}.

\hypertarget{routing-semantics}{%
\subsection{Routing Semantics}\label{routing-semantics}}

The v1 routing engine receives:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{recipient identifier}
\NormalTok{amount\_sats}
\NormalTok{verified SignedPaymentProfile}
\NormalTok{fee environment}
\end{Highlighting}
\end{Shaded}

The current reference policy is:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Prefer Lightning for small amounts when a Lightning method is
  available.
\item
  Consider on-chain when fee conditions make it acceptable and an
  on-chain method is available.
\item
  Consider Ark when an Ark method is available.
\item
  Return \texttt{no\_route} when no available method passes policy.
\end{enumerate}

The response MUST include a human-readable \texttt{reason} describing
the selected route.

Routing policy MAY evolve without changing the quote response wire
shape.

\hypertarget{mandatory-transparency-composition}{%
\subsection{Mandatory Transparency
Composition}\label{mandatory-transparency-composition}}

The standalone daemon MUST NOT route \texttt{/v1/quote},
\texttt{/v1/pay} or \texttt{/v1/preview} from a self-contained signed
profile alone. These endpoints use the same result as
\texttt{/v1/resolve} and verify, in order: canonical profile signature
and expiry, identifier history, key continuity, latest profile/event
binding, inclusion in the exact signed checkpoint, consistency with the
\texttt{log\_id} pin, operator-key continuity, and payment-method
ownership. Failure is terminal and MUST NOT fall back to the legacy
resolver chain.

Name-event hashing uses two distinct values:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{signing\_payload\_hash = SHA256("SatsPathNameEventPayloadV1" || canonical\_json(unsigned\_event))}
\NormalTok{owner\_signature      = Schnorr("SatsPathNameEventSignatureV1\textbackslash{}n" || hex(signing\_payload\_hash))}
\NormalTok{signed\_event\_hash    = SHA256("SatsPathSignedNameEventV1" || canonical\_json(full\_signed\_event))}
\NormalTok{leaf\_hash            = SHA256(0x00 || raw(signed\_event\_hash))}
\end{Highlighting}
\end{Shaded}

All quoted strings above are exact UTF-8 bytes with no NUL separator.
Hex is lowercase. \texttt{previous\_event\_hash} is the preceding
\texttt{signed\_event\_hash}. Registration uses sequence 0; every
accepted mutation increments exactly once, and profile, event and
rotation sequences MUST match.

An inclusion result is valid only if proof root/size equal checkpoint
root/size, the leaf is derived from the requested signed event hash, the
Merkle audit path verifies, and the checkpoint's 64-byte secp256k1
Schnorr signature verifies. Pins are keyed by stable \texttt{log\_id}; a
changed operator public key requires old-key authorization and new-key
acceptance in a versioned operator rotation.

\hypertarget{payment-handoff}{%
\subsection{Payment Handoff}\label{payment-handoff}}

SatsPath v1 returns public payment payloads. It does not spend funds.

An implementation MAY expose a local API such as:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{POST /v1/pay}
\end{Highlighting}
\end{Shaded}

This API MUST still return a protocol decision and a wallet handoff. It
MUST NOT sign, broadcast, or custody funds unless a future protocol
version explicitly defines an execution extension.

\hypertarget{transport-neutrality}{%
\subsection{Transport Neutrality}\label{transport-neutrality}}

SatsPath objects can move over multiple transports:

\begin{itemize}
\tightlist
\item
  Local registry files.
\item
  HTTPS well-known endpoints.
\item
  BIP-353 DNS payment instructions.
\item
  Nostr/NIP-05 profile announcements.
\item
  Pear/Holepunch peer transport.
\item
  Manual file export/import.
\end{itemize}

All transports carry the same protocol objects and MUST be verified
using the same profile verification rules.

\hypertarget{nostr-transport-profile}{%
\subsubsection{Nostr Transport Profile}\label{nostr-transport-profile}}

Nostr transport uses NIP-05 to bind an identifier domain to a Nostr
pubkey and relay list. The SatsPath profile itself is carried in a
replaceable Nostr event:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{\{}
  \DataTypeTok{"kind"}\FunctionTok{:} \DecValTok{30078}\FunctionTok{,}
  \DataTypeTok{"pubkey"}\FunctionTok{:} \StringTok{"\textless{}nip05 nostr pubkey hex\textgreater{}"}\FunctionTok{,}
  \DataTypeTok{"tags"}\FunctionTok{:} \OtherTok{[}
    \OtherTok{[}\StringTok{"d"}\OtherTok{,} \StringTok{"satspath{-}profile:alice@example.com"}\OtherTok{]}
  \OtherTok{]}\FunctionTok{,}
  \DataTypeTok{"content"}\FunctionTok{:} \StringTok{"\{}\CharTok{\textbackslash{}"}\StringTok{profile}\CharTok{\textbackslash{}"}\StringTok{:\{...\},}\CharTok{\textbackslash{}"}\StringTok{signature}\CharTok{\textbackslash{}"}\StringTok{:}\CharTok{\textbackslash{}"}\StringTok{3044...}\CharTok{\textbackslash{}"}\StringTok{\}"}
\FunctionTok{\}}
\end{Highlighting}
\end{Shaded}

Resolution MUST verify:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The NIP-05 document maps the local identifier part to the event author
  pubkey.
\item
  The event kind is \texttt{30078}.
\item
  The event author is the NIP-05 pubkey.
\item
  The \texttt{d} tag is
  \texttt{satspath-profile:\textless{}canonical\ identifier\textgreater{}}.
\item
  The event content parses as \texttt{SignedPaymentProfile}.
\item
  The SatsPath profile signature and expiry checks pass.
\end{enumerate}

Nostr event signatures do not replace SatsPath profile signatures. Nostr
is a discovery transport; SatsPath profile verification remains
mandatory.

Pear/Holepunch is specified as an optional wire transport in
\href{./wire_p2p.md}{wire\_p2p.md}.

\hypertarget{security-requirements}{%
\subsection{Security Requirements}\label{security-requirements}}

Implementations MUST:

\begin{itemize}
\tightlist
\item
  Verify signed profiles before routing.
\item
  Reject malformed public keys and signatures.
\item
  Reject expired profiles.
\item
  Reject private material in public fields.
\item
  Treat resolver output as untrusted until verified.
\item
  Fail closed for DNSSEC-required flows unless explicitly placed into an
  insecure development mode.
\item
  Never convert an invite into a payable route without re-resolving a
  signed profile.
\end{itemize}

Implementations SHOULD:

\begin{itemize}
\tightlist
\item
  Display whether a recipient was verified.
\item
  Display the selected rail and routing reason.
\item
  Separate route decision from payment execution.
\item
  Keep resolver failures observable for debugging.
\end{itemize}
