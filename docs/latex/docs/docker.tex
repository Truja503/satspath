\hypertarget{layer-caching-strategy-rust}{%
\subsubsection{Layer caching strategy
(Rust)}\label{layer-caching-strategy-rust}}

The Rust build uses
\href{https://github.com/LukeMathWalker/cargo-chef}{\texttt{cargo-chef}}:

\begin{verbatim}
Layer 1: cargo-chef planner  → only re-runs when Cargo.toml/Cargo.lock change
Layer 2: cargo-chef cacher   → pre-builds all deps (very slow, cached)
Layer 3: builder             → compiles src/ (fast, re-runs on src change)
Layer 4: runtime             → copies single binary (~25 MB)
\end{verbatim}

This means typical CI rebuilds take \textbf{\textasciitilde30 seconds}
instead of 10+ minutes.

\item[$\square$]

\item[$\square$]

\hypertarget{troubleshooting}{%
\subsection{Troubleshooting}\label{troubleshooting}}

\textbf{\texttt{cargo:\ command\ not\ found} in CI} → The build runs
inside the container; you don't need Cargo on the host.

\textbf{\texttt{Error:\ no\ such\ service:\ ark-bridge}} → Add
\texttt{-\/-profile\ bridge} flag:
\texttt{docker\ compose\ -\/-profile\ bridge\ up}.

\textbf{\texttt{Permission\ denied:\ /data}} → The
\texttt{satspath-data} volume ownership may be wrong. Run:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{docker}\NormalTok{ compose run }\AttributeTok{{-}{-}rm} \AttributeTok{{-}{-}user}\NormalTok{ root satspath{-}cli chown }\AttributeTok{{-}R}\NormalTok{ 10001:10001 /data}
\end{Highlighting}
\end{Shaded}

\textbf{Build fails on \texttt{is\_multiple\_of} (pre-existing)} → This
is a known pre-existing issue in
\texttt{satspath-router/src/lightning.rs} using a nightly-only Rust API.
It does not affect the \texttt{satspath} CLI binary build, only
\texttt{satspath-router} library checks on stable Rust. Unrelated to
Docker.
