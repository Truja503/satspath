\hypertarget{satspath-v2-verified-replication-failover}{%
\section{SatsPath v2 Verified Replication \&
Failover}\label{satspath-v2-verified-replication-failover}}

\hypertarget{overview}{%
\subsection{Overview}\label{overview}}

Cryptography prevents a server from forging identity state, but cannot
prevent censorship or downtime. Server-to-server replication ensures
availability, monitoring, and sovereign operation without reintroducing
trust in whichever mirror responds fastest.

\hypertarget{replication-model}{%
\subsection{Replication Model}\label{replication-model}}

SatsPath uses a \textbf{pull-based} replication model where replicas
periodically fetch and verify updates from the primary authority.

\hypertarget{roles}{%
\subsubsection{Roles}\label{roles}}

\begin{itemize}
\tightlist
\item
  \textbf{Primary}: The sole authority that accepts and commits signed
  name events. Only the primary appends to the log.
\item
  \textbf{Replica}: Ingests, verifies, and durably stores the primary's
  data. A replica NEVER authors events; it only mirrors verified state.
\end{itemize}

\hypertarget{ingestion-pipeline}{%
\subsubsection{Ingestion Pipeline}\label{ingestion-pipeline}}

A replica must ingest and verify, in order: 1. Namespace descriptor and
policy epoch. 2. Signed name events (verified against
\texttt{verify\_event\_transition}). 3. Append-only log entries and
checkpoints (verified via \texttt{verify\_checkpoint\_transition}). 4.
Compact consistency proofs (verified via
\texttt{verify\_consistency\_proof}). 5. Current-state map snapshots or
deterministic updates. 6. Witness cosignatures. 7. Operator and
namespace-key transitions.

A replica serves data \textbf{only after full verification and durable
commit}.

\hypertarget{failover-rules}{%
\subsection{Failover Rules}\label{failover-rules}}

\begin{itemize}
\tightlist
\item
  Discovery may list multiple endpoints with explicit priority/role.
\item
  Any endpoint may serve a proof envelope, but the client verifies the
  same namespace/log/witness policy.
\item
  Prefer a newer policy-valid checkpoint; \textbf{never accept tree-size
  rollback} because the primary is unavailable.
\item
  A stale replica may serve within a defined maximum staleness window
  and must disclose its checkpoint age.
\item
  Two same-size/different-root views are a \textbf{critical
  equivocation}, not a normal conflict.
\end{itemize}

\hypertarget{caching-rules}{%
\subsection{Caching Rules}\label{caching-rules}}

\begin{itemize}
\tightlist
\item
  Cache keys include: namespace, descriptor epoch, \texttt{log\_id},
  tree size/root, and identifier.
\item
  Cached positive and negative answers cannot outlive
  descriptor/checkpoint freshness policy.
\item
  Backfill can resume from a pinned checkpoint with a consistency proof;
  full trust reset is forbidden.
\end{itemize}

\hypertarget{security-properties}{%
\subsection{Security Properties}\label{security-properties}}

\begin{itemize}
\tightlist
\item
  Replication transports \textbf{public identity data only}. No private
  keys cross any boundary.
\item
  A corrupted or malicious replica cannot forge, roll back, or mix
  state.
\item
  Conflicting authoritative views produce evidence and halt routing.
\end{itemize}
