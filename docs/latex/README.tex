\hypertarget{satspath}{%
\section{SatsPath}\label{satspath}}

\textbf{A transport-neutral Bitcoin payment discovery and routing
protocol.}

\begin{quote}
\textbf{CAUTION:} \textbf{EXPERIMENTAL SOFTWARE --- DO NOT USE WITH REAL
FUNDS.} SatsPath v2 is currently undergoing internal conformance testing
(Issue \#60). It must not be deployed for real economic activity until
the v2 conformance suite is finalized and an external cryptographic
audit gate is deliberately cleared.
\end{quote}

The standalone daemon includes an experimental key-transparency log and
Merkle explorer. Quote, pay and preview fail closed unless the profile
is included in the exact signed checkpoint and consistent with the local
\texttt{log\_id} pin. It is unaudited; see
\href{docs/key_transparency.md}{the architecture and limitations}.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{problem}{%
\subsection{Problem}\label{problem}}

Bitcoin has multiple payment rails --- Lightning, on-chain, Ark, LNURL,
BOLT12, Silent Payments --- each with different trade-offs on speed,
cost, and privacy. Users and apps must manually decide which rail to
use, and there is no universal way to discover payment methods from a
human-readable identifier.

\hypertarget{solution}{%
\subsection{Solution}\label{solution}}

SatsPath maps human-readable identifiers
(e.g.~\texttt{alice@example.com}) to \textbf{signed payment profiles}
containing all available payment methods. A routing engine selects the
best rail automatically based on amount, on-chain fees, and available
methods.

Identity keys generated by SatsPath are used exclusively for signing
profiles and proving ownership. \textbf{SatsPath does NOT generate
wallet private keys, seeds, or custody keys for funds.} SatsPath is a
resolution and routing layer --- not a wallet, not a custodian.

SatsPath is specified as a transport-neutral protocol. Pear/Holepunch
P2P is one optional transport for signed profiles, not the protocol
itself. Start with \url{docs/protocol.md}, \url{docs/resolvers.md},
\url{docs/wire_p2p.md}, and \url{docs/implementations.md}.

The core flow is:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{identifier {-}\textgreater{} resolver chain {-}\textgreater{} signed profile {-}\textgreater{} signature check {-}\textgreater{} route decision {-}\textgreater{} QR / wallet handoff}
\end{Highlighting}
\end{Shaded}

Resolvers can use local files, HTTPS well-known endpoints, BIP-353 DNS,
Nostr/NIP-05, or optional P2P. A receiver publishes the same signed
SatsPath profile over any of those transports. A sender only trusts it
after SatsPath verifies the profile signature.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{current-functional-surface}{%
\subsection{Current Functional
Surface}\label{current-functional-surface}}

\begin{itemize}
\tightlist
\item
  Resolve \texttt{alice@example.com} to a signed payment profile through
  the resolver chain.
\item
  Encode/decode universal payment URIs
  (\texttt{satspath:v1:\textless{}base64url\_json\textgreater{}}).
\item
  Sign profiles with secp256k1 identity keys.
\item
  Verify profile signatures before routing.
\item
  Resolve LNURL-pay endpoints and fetch BOLT11 invoices securely.
\item
  Select the best payment rail (Lightning → On-chain → Ark
  preview/intents).
\item
  Return a stable \texttt{QuoteResponse} with \texttt{ok},
  \texttt{not\_registered}, \texttt{no\_route}, or
  \texttt{invalid\_signature}.
\item
  Produce a public payment payload / QR via CLI preview or
  \texttt{satspathd} wallet handoff.
\item
  Fetch real-time on-chain fee estimates from mempool.space.
\item
  Generate safe payment previews and Ark route intents; Ark swaps are
  not claimed as complete unless explicitly testnet-executed and
  supported by the bridge.
\item
  Resolve DNSSEC-backed \textbf{BIP-353} payment instructions
  (\texttt{₿user@domain}) for domains the receiver controls --- see
  \url{docs/bip353_dns_resolution.md}.
\item
  Resolve SatsPath profiles over \textbf{Nostr/NIP-05} without P2P:
  NIP-05 discovers a Nostr pubkey and relays, then relays are queried
  for a signed SatsPath profile event.
\item
  Generate invite links for unregistered users (receiver generates their
  own keys).
\item
  Run a local daemon (\texttt{satspathd}) that exposes
  \texttt{/v1/node}, \texttt{/v1/quote}, \texttt{/v1/pay}, and
  \texttt{/v1/dns/resolve}.
\item
  Full CLI: \texttt{init}, \texttt{register}, \texttt{show},
  \texttt{encode}, \texttt{decode}, \texttt{quote}, \texttt{pay},
  \texttt{invite}, \texttt{dns\ resolve}, \texttt{demo}.
\item
  \textbf{Self-Hosting}: Sovereign server deployment and DNS operator
  onboarding (\texttt{satspath\ server\ init/check}). See
  \url{deploy/README.md} for Docker Compose and TLS proxy instructions.
\end{itemize}

\begin{quote}
SatsPath can resolve DNSSEC-backed BIP-353 payment instructions for
domains the receiver controls. For consumer email addresses like
\texttt{gmail.com}, SatsPath uses platform verification / the invite
flow instead, because the user cannot publish DNS records under
\texttt{gmail.com}. BIP-353 resolution is \textbf{mainnet preview only}:
SatsPath resolves and displays instructions but never pays, signs, or
broadcasts.
\end{quote}

\hypertarget{resolver-chain}{%
\subsubsection{Resolver Chain}\label{resolver-chain}}

The default resolver chain is:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{local registry {-}\textgreater{} BIP{-}353 {-}\textgreater{} HTTPS well{-}known {-}\textgreater{} Nostr/NIP{-}05}
\end{Highlighting}
\end{Shaded}

Optional Pear/Holepunch P2P can be used as another transport, but the
protocol does not depend on it.

For Nostr, publish:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  A NIP-05 record at
  \texttt{https://\textless{}domain\textgreater{}/.well-known/nostr.json?name=\textless{}user\textgreater{}}
  that maps \texttt{user} to a Nostr pubkey and relay list.
\item
  A Nostr kind \texttt{30078} event by that pubkey with tag:
\end{enumerate}

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{d = satspath{-}profile:\textless{}user@domain\textgreater{}}
\end{Highlighting}
\end{Shaded}

The event \texttt{content} is the JSON \texttt{SignedPaymentProfile}.
Senders then resolve the identifier, verify the SatsPath profile
signature, route, and get the QR/payment payload.

Consumer email domains such as \texttt{gmail.com} cannot be used for DNS
or NIP-05 publication unless the user controls the domain endpoint. For
those identifiers, the current behavior is invite flow or a future
platform-verification resolver.

\hypertarget{email-identifiers-vs-verified-identifiers}{%
\subsubsection{Email identifiers vs verified
identifiers}\label{email-identifiers-vs-verified-identifiers}}

SatsPath can use an email-shaped value as the human-readable identifier.
That does not automatically verify the inbox.

\begin{itemize}
\tightlist
\item
  A signed profile proves control of the SatsPath protocol identity key.
\item
  DNSSEC/BIP-353 or Nostr/NIP-05 can prove domain-controlled
  publication.
\item
  A consumer email address such as \texttt{user@gmail.com} needs a
  platform challenge flow before it can be marked as an
  identifier-verified profile.
\item
  Until that exists, consumer email addresses are treated as identifiers
  for lookup and invite delivery, not as verified payment identities.
\end{itemize}

\tightlist

\end{enumerate}

\end{Highlighting}
\end{Shaded}

\end{enumerate}

\begin{Shaded}
\begin{Highlighting}[]

  \DataTypeTok{"kind"}\FunctionTok{:} \DecValTok{30078}\FunctionTok{,}
  \DataTypeTok{"tags"}\FunctionTok{:} \OtherTok{[[}\StringTok{"d"}\OtherTok{,} \StringTok{"satspath{-}profile:alice@example.com"}\OtherTok{]]}\FunctionTok{,}

\FunctionTok{\}}
\end{Highlighting}

\texttt{content} is the exact JSON \texttt{SignedPaymentProfile}
exported by SatsPath.

Sender side:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{satspath}\NormalTok{ quote alice@example.com 250 }\AttributeTok{{-}{-}mainnet{-}preview} \AttributeTok{{-}{-}json}
\end{Highlighting}
\end{Shaded}

The resolver chain discovers the Nostr pubkey/relays through NIP-05,
fetches the SatsPath profile event, verifies the SatsPath signature, and
returns the normal \texttt{QuoteResponse} with a QR/payment payload.

For \texttt{rodrigodiazgt7@gmail.com}, neither DNS nor NIP-05 can be
published by the user under \texttt{gmail.com}. That identifier
currently resolves through invite flow unless a future platform resolver
verifies Gmail ownership and publishes a signed profile through a
supported transport.

\hypertarget{what-this-prototype-does-not-do-yet}{%
\subsection{What this prototype does NOT do
yet}\label{what-this-prototype-does-not-do-yet}}

\begin{itemize}
\tightlist
\item
  Execute real Lightning, on-chain, or Ark payments. The experimental
  swap engine is \textbf{testnet-only scaffolding that previews swap
  intent}; it does not complete, direct, claim, or refund swaps, and
  must never be used on mainnet.
\item
  Enable mainnet Ark execution.
\item
  Verify email or domain ownership during registration.
\item
  Publish profiles to Nostr from the Rust CLI. The resolver can read
  Nostr events, but publishing still needs a Nostr client or a future
  CLI command.
\item
  Provide a decentralized global registry. SatsPath uses resolver
  transports; it does not have a single canonical registry.
\item
  Support key rotation or profile revocation.
\item
  Implement BOLT12 invoice fetching.
\item
  Support Silent Payments or Split Payments.
\item
  Provide a production wallet UI.
\end{itemize}

\hypertarget{safe-path-mainnet-preview-vs-experimental-execution}{%
\subsection{Safe Path (Mainnet Preview) vs Experimental
Execution}\label{safe-path-mainnet-preview-vs-experimental-execution}}

The \textbf{Safe Path} (Mainnet Preview) is active by default and
allowed:

\begin{itemize}
\tightlist
\item
  Resolving public data only.
\item
  Fetching and resolving LNURL-pay metadata.
\item
  Requesting BOLT11 invoices from LNURL callbacks securely.
\item
  Presenting the invoice as a QR code or payment pointer for the user to
  pay with their own wallet.
\item
  Profile signature and expiry checks.
\item
  Public ownership proof checks where available.
\item
  BIP21 on-chain URI generation.
\item
  Ark public pointer / intent URI generation.
\end{itemize}

The \textbf{Experimental Path} (Automatic Execution via Swaps/Ark) is
isolated and restricted:

\begin{itemize}
\tightlist
\item
  Requires explicit \texttt{-\/-experimental-swaps} and
  \texttt{-\/-testnet} flags.
\item
  Mainnet execution is strictly disabled (no
  \texttt{-\/-execute-mainnet} flag exists).
\item
  No automatic payment execution exists on mainnet.
\item
  No transaction signing or broadcasting path is exposed.
\item
  No seed phrases, xprv/tprv, macaroons, certs, API secrets, claim keys,
  or refund keys are accepted into mainnet preview output.
\end{itemize}

\hypertarget{security-model}{%
\subsection{Security model}\label{security-model}}

\begin{itemize}
\tightlist
\item
  \textbf{Keys are local.} The only private keys SatsPath generates are
  \textbf{identity keys used to sign public payment profiles} --- they
  are not wallet spending keys, seeds, or custody keys, and they do not
  control funds. They are stored only on the user's machine in
  \texttt{.satspath/keys.json}, which is git-ignored and never
  transmitted.
\item
  \textbf{Signatures are mandatory.} Every payment profile is signed
  with the owner's identity key. Signature verification happens before
  routing.
\item
  \textbf{Public profiles only.} The registry stores only public data:
  pubkeys, addresses, and signatures.
\item
  \textbf{Invite, don't proxy.} For unknown users, SatsPath creates an
  invite. The receiver generates their own keys.
\end{itemize}

\hypertarget{hackathon-scope}{%
\subsection{Hackathon scope}\label{hackathon-scope}}

This prototype was built during a hackathon to demonstrate:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  A working secp256k1-signed payment profile format with expiration.
\item
  A universal URI encoding scheme for payment requests.
\item
  An automatic payment rail selector using real mempool.space fee data.
\item
  A privacy-aware profile with multiple on-chain addresses.
\item
  An invite flow that preserves receiver key sovereignty.
\item
  A fail-closed, encrypted swap storage engine (behind
  \texttt{-\/-experimental-swaps}).
\end{enumerate}

It is \textbf{not production-ready}. The registry is local, payments are
simulated (unless experimental flags are used), and domain verification
is not implemented.
