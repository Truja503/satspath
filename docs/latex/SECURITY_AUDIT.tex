\section{SatsPath Security Audit
Report}\label{satspath-security-audit-report}}

\textbf{Target:} SatsPath Protocol v1 Prototype (Resolution + Routing +
Experimental Swaps) \textbf{Scope:} White-box code review (Rust crates +
TypeScript Ark Bridge) + Black-box protocol analysis \textbf{Date:}
2026-06-30 \textbf{Classification:} Hackathon Prototype --- Do Not Use
With Real Funds

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{executive-summary}{%
\subsection{Executive Summary}\label{executive-summary}}

SatsPath is a well-designed resolution and routing layer with strong
cryptographic foundations. The codebase demonstrates \textbf{excellent
security hygiene} for a prototype: mandatory signature verification,
fail-closed defaults, private material detection, encrypted swap
storage, and comprehensive ownership proof infrastructure.

However, as a \textbf{prototype}, it has known gaps documented in
\texttt{threat\_model.md} and several \textbf{critical findings} that
must be addressed before any mainnet deployment.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{1. 🔴 CRITICAL: Fee Estimation Trust Violation --- Single
Point of
Failure}\label{critical-fee-estimation-trust-violation-single-point-of-failure}}

\textbf{Location:} \texttt{crates/satspath-router/src/fees.rs:28-45}
\textbf{Impact:} Routing decisions for on-chain vs Ark are based on
\texttt{mempool.space} API. If attacker controls DNS or MITM, they can
force all large payments to Ark (or on-chain at high fees).

blockstream.info + local node) - Consensus: reject if sources disagree
by \textgreater{} 2x - Optional: pinned TLS certs for fee API endpoints
- User-configurable fee source with local Bitcoin Core RPC as ground
truth

\textbf{Impact:} Attacker registers \texttt{alíce@example.com} (with

\hypertarget{high-no-replay-protection-on-payment-profiles}{%
\subsubsection{8. 🟠 HIGH: No Replay Protection on Payment
Profiles}\label{high-no-replay-protection-on-payment-profiles}}

\textbf{Location:} \texttt{crates/satspath-core/src/profile.rs:116-141},
\texttt{crypto.rs:33-47} \textbf{Impact:} Old signed profile (with old
methods) can be replayed indefinitely until \texttt{expires\_at}.

\textbf{Scenario:} User rotates keys, publishes new profile. Attacker
intercepts old profile and serves it to payers. Payers route to old
Lightning Address (attacker-controlled).

\textbf{Fix:} - Add \texttt{nonce} or \texttt{sequence} to profile,
require strictly increasing - Short \texttt{expires\_at} (e.g., 24h)
with automatic refresh - Client-side pinning: remember
\texttt{identity\_pubkey} + \texttt{updated\_at} per alias

\hypertarget{protocol-invite-flow-no-rate-limiting}{%
\subsubsection{20. 🔵 PROTOCOL: Invite Flow --- No Rate
Limiting}\label{protocol-invite-flow-no-rate-limiting}}

\textbf{Spec:} \texttt{docs/protocol.md:211-232}

Attacker can generate unlimited invites for target alias, causing: -
Spam in receiver's claim inbox - Registry pollution (if invites stored
server-side) - Social engineering: ``You received 10 BTC, claim now!''

\texttt{expires\_at} to invite (currently only in \texttt{InviteRecord},
not \texttt{Invite}).

\subsubsection{21. 🔵 PROTOCOL: BIP-353 --- Consumer Email Domains
Excluded}\label{protocol-bip-353-consumer-email-domains-excluded}}

\textbf{Spec:} \texttt{docs/protocol.md:250-258}

\begin{quote}
``Consumer email domains (e.g.~gmail.com) cannot use BIP-353 --- they
fall back to platform verification / the invite flow.''
\end{quote}

\textbf{Implication:} 90\%+ of users (Gmail, Outlook, Yahoo)
\textbf{cannot use DNSSEC resolution}. They rely on centralized platform
verification, defeating decentralization.

\textbf{Fix:} Document this limitation clearly. Explore Nostr NIP-05 as
alternative for consumer domains.

Fetching}\label{protocol-mainnet-preview-no-execution-but-invoice-fetching}}

\textbf{Spec:} \texttt{docs/protocol.md:178-205}

\begin{quote}

invoice string only when explicitly fetched by the caller''
\end{quote}

\textbf{Risk:} Caller fetches BOLT11 invoice → displays to user → user

different node (if LNURL compromised)

expired, and (if possible) matches receiver pubkey in profile.
