\hypertarget{what-engine-v0-is}{%
\subsection{What Engine v0 is}\label{what-engine-v0-is}}

SatsPath Engine v0 is an experimental signed payment resolver and
router. It is \textbf{not} a production wallet or automatic payment
engine.

It can: - Resolve a local or peer-registered signed profile - Select a
payment rail (Lightning, on-chain, Ark) based on live mempool fees -
Fetch a real LNURL invoice and display a scannable QR code - Display a
BIP-21 URI with a QR code for on-chain payments - Preview which swap
directive would be needed (testnet only, no execution)

It cannot (and intentionally does not): - Move funds automatically -
Sign Bitcoin transactions - Broadcast anything to the network - Store or
generate seed phrases - Execute mainnet swaps

\hypertarget{swap-engine-status-engine-v0-scaffolding-only}{%
\subsection{Swap engine status --- Engine v0 scaffolding
only}\label{swap-engine-status-engine-v0-scaffolding-only}}

The \texttt{satspath-swaps} crate is an \textbf{experimental
testnet-only scaffold} for Boltz Exchange v2 swap integration.

\textbf{Claim and refund transaction construction is not implemented
(Engine v1 work).}\\
\textbf{Mainnet payment execution is not implemented.}

\begin{itemize}
\tightlist
\item
  PSBT signing is not implemented
\item
  Mainnet execution paths are closed
\item
  The swap engine is only reachable via
  \texttt{-\/-experimental-swaps\ -\/-testnet}
\item
  Without those flags, no swap code runs at all
\end{itemize}

\hypertarget{default-behavior-what-satspath-pay-does}{%
\subsection{\texorpdfstring{Default behavior --- what
\texttt{satspath\ pay}
does}{Default behavior --- what satspath pay does}}\label{default-behavior-what-satspath-pay-does}}

\begin{verbatim}
satspath pay rodrigodiazgt7@gmail.com 1000
\end{verbatim}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Resolves the alias to a signed local profile
\item
  Verifies the identity signature (ECDSA/secp256k1)
\item
  Fetches live mempool fee rates from mempool.space
\item
  Selects the best payment rail based on fees and amount
\item
  For Lightning: performs LNURL-pay two-step fetch → real BOLT11 invoice
  → QR
\item
  For on-chain: builds BIP-21 URI → QR
\end{enumerate}

\textbf{SatsPath does not send any funds. No keys are touched. No
transactions are signed or broadcast. The displayed invoice/URI is for
the user to scan with their own wallet.}

\hypertarget{experimental-swap-engine-testnet-intent-preview-only}{%
\subsection{Experimental swap engine --- testnet intent preview
only}\label{experimental-swap-engine-testnet-intent-preview-only}}

\begin{verbatim}
satspath pay rodrigodiazgt7@gmail.com 1000 --experimental-swaps --testnet
\end{verbatim}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Same resolution and routing
\item
  Shows swap directive intent only
\item
  Does NOT execute the swap
\item
  Does NOT build any transaction
\item
  \texttt{-\/-experimental-swaps} without \texttt{-\/-testnet} is
  rejected with a hard error
\end{enumerate}

\textbf{No funds are moved. This is a preview of what a swap would look
like.}

\hypertarget{persistence-and-secrets}{%
\subsection{Persistence and secrets}\label{persistence-and-secrets}}

\begin{itemize}
\tightlist
\item
  All local state lives in \texttt{.satspath/} (gitignored --- never
  committed)
\item
  \texttt{LocalPeerRegistry} stores SHA-256(canonical\_identifier) as
  the DB key --- raw email is never stored as primary key
\item
  \texttt{SwapStore} writes sensitive swap secrets
  (\texttt{preimage\_hex}, \texttt{refund\_key\_hex},
  \texttt{claim\_key\_hex}) only when an AES-256-GCM encryption key is
  provided
\item
  Writing sensitive swap material to plaintext storage is rejected at
  the record level
\item
  No private keys, seeds, macaroons, or API tokens are committed to this
  repository
\end{itemize}

\hypertarget{ark-bridge-status}{%
\subsection{ARK bridge status}\label{ark-bridge-status}}

The \texttt{ark-bridge/} directory contains a JSON-RPC bridge skeleton
that would connect the Rust CLI to the ARK client-side validation SDK.

\textbf{Current status:} - The TypeScript bridge compiles and handles
all protocol methods with stub responses - VTXO DAG validation is not
implemented (requires the full Ark SDK --- tracked as Engine v1) - The
Rust \texttt{ArkBridge::spawn()} call is non-fatal: if the bridge is
unavailable, the CLI continues in pointer/intent mode and prints a clear
warning - Ark payments in Engine v0 display the payment pointer and an
explicit experimental warning

\hypertarget{wallet-integration-post-quantum-security-fase-2-3}{%
\subsection{Wallet Integration \& Post-Quantum Security (Fase 2 \&
3)}\label{wallet-integration-post-quantum-security-fase-2-3}}

The Arkade Money Wallet has been fully integrated with the SatsPath
protocol in the frontend via WASM.

\begin{itemize}
\tightlist
\item
  \textbf{Post-Quantum Cryptography (PQC):} The protocol now uses a
  hybrid signature scheme (\texttt{ML-DSA-65-Schnorr}) for generating
  and verifying identity keys. The \texttt{pqc\_seed} is encrypted and
  stored locally via the Web Crypto API alongside the classical identity
  key.
\item
  \textbf{SSRF Protection:} Resolvers (both WASM and Core) now strictly
  validate URLs and block loopback, private, and internal metadata IP
  ranges to prevent malicious profile endpoints from exploiting the
  client's internal network.
\item
  \textbf{Nostr Profiles:} The wallet now successfully builds, signs,
  and publishes NIP-78 SatsPath profiles to Nostr relays.
\item
  \textbf{Routing \& Execution:} The Wallet's Send Flow uses the
  SatsPath resolver WASM module to dynamically quote and fallback
  between Lightning, On-chain, and Ark endpoints seamlessly.
\end{itemize}

\hypertarget{phase-4-advanced-rails-ark-verification-silent-payments-bolt12}{%
\subsection{Phase 4: Advanced Rails (Ark Verification, Silent Payments,
BOLT12)}\label{phase-4-advanced-rails-ark-verification-silent-payments-bolt12}}

\hypertarget{ark-vtxo-zero-trust-verification}{%
\subsubsection{1. Ark VTXO Zero-Trust
Verification}\label{ark-vtxo-zero-trust-verification}}

\begin{itemize}
\tightlist
\item
  \textbf{Ported Validation Logic:} Copied and adapted the client-side
  DAG verification logic from \texttt{ARK/src} into
  \texttt{wallet/src/lib/ark-verification/}.
\item
  \textbf{v2 Upgrades:} Upgraded all references to
  \texttt{@scure/btc-signer} v2, \texttt{@noble/hashes} v2, and
  \texttt{@noble/curves} v2, removing legacy \texttt{Buffer}
  dependencies in favor of \texttt{Uint8Array}.
\item
  \textbf{Background Validation:} Integrated a zero-trust,
  fire-and-forget background verification hook in \texttt{wallet.tsx}
  using the \texttt{verifyNewVtxos()} helper. Every time
  \texttt{VTXO\_UPDATE} is triggered by the service worker, the wallet
  asynchronously verifies the full DAG of the new VTXOs without blocking
  the UI.
\end{itemize}

\hypertarget{bip-352-silent-payments-support}{%
\subsubsection{2. BIP-352 Silent Payments
Support}\label{bip-352-silent-payments-support}}

\begin{itemize}
\tightlist
\item
  \textbf{Core Integration:} Confirmed the
  \texttt{silent\_payment\_pubkey} configuration exists in
  \texttt{crates/satspath-core/src/profile.rs} onchain methods.
\item
  \textbf{WASM Router Updates:} Modified the WASM router
  \texttt{satspath-wasm/src/router.rs} to format the \texttt{bitcoin:}
  URI using \texttt{sp1...} if the \texttt{silent\_payment\_pubkey} is
  defined for a given onchain method, ensuring privacy-preserving
  static-address behavior.
\item
  \textbf{Wallet Hookup:} Updated \texttt{satspath.ts} to seamlessly
  parse \texttt{silent\_payment\_pubkey} from the method outputs.
\end{itemize}

\hypertarget{bolt12-http-scaffold}{%
\subsubsection{3. BOLT12 HTTP Scaffold}\label{bolt12-http-scaffold}}

\begin{itemize}
\tightlist
\item
  \textbf{Scaffold Function:} Added a configurable HTTP proxy scaffold
  via \texttt{crates/satspath-wasm/src/bolt12.rs} to allow resolving
  BOLT12 offers to real BOLT11 invoices.
\item
  \textbf{Router Support:} The router was enhanced to inspect the
  \texttt{bolt12} field within \texttt{LightningMethod} and fetch the
  proxy asynchronously as a fallback when an LNURL string isn't
  available.
\end{itemize}

\hypertarget{luxf3gica-y-rendimiento-unit-tests-benchmarks}{%
\subsection{Lógica y Rendimiento (Unit Tests \&
Benchmarks)}\label{luxf3gica-y-rendimiento-unit-tests-benchmarks}}

De acuerdo a las prioridades establecidas, enfocamos los esfuerzos
exclusivamente en la lógica de negocio en el backend de Rust (Crates).

\hypertarget{pruebas-unitarias-e-integraciuxf3n-91-tests-passing}{%
\subsubsection{1. Pruebas Unitarias e Integración (91 tests
passing)}\label{pruebas-unitarias-e-integraciuxf3n-91-tests-passing}}

\begin{itemize}
\tightlist
\item
  \textbf{SSRF (Fase 1):} Verificamos matemáticamente que el validador
  en \texttt{ssrf.rs} bloquee rangos IPV4 e IPV6 locales/privados
  (127.0.0.0/8, 10.0.0.0/8, etc.) y endpoints de metadata en la nube
  (\texttt{169.254.169.254}).
\item
  \textbf{Silent Payments (Fase 4):} Probamos el router WASM comprobando
  que si el usuario registra una llave pública de pagos silenciosos
  (\texttt{sp1...}), el payload generado prioriza esta llave y la
  inyecta correctamente como \texttt{bitcoin:sp1...?amount=X}.
\item
  \textbf{BOLT12 (Fase 4):} Extrajimos el constructor de URIs del proxy
  proxy a una función pura testeable en Rust.
\item
  \textbf{Correcciones transversales:} Resolvimos múltiples fallas de
  compilación en el \texttt{satspath-router} y el CLI \texttt{satspathd}
  asegurando que todos inicialicen los nuevos campos híbridos
  (\texttt{hybrid\_pubkey}, \texttt{pqc\_required}) del
  \texttt{PaymentProfile}.
\end{itemize}

\hypertarget{criterion-benchmarks-ml-dsa-schnorr}{%
\subsubsection{2. Criterion Benchmarks (ML-DSA +
Schnorr)}\label{criterion-benchmarks-ml-dsa-schnorr}}

Ejecutamos con éxito los benchmarks definidos para la suite
criptográfica híbrida PQC, arrojando métricas de excelente rendimiento:
- \textbf{Keygen:} \texttt{\textasciitilde{}347\ µs} - \textbf{Signing:}
\texttt{\textasciitilde{}721\ µs} - \textbf{Verifying:}
\texttt{\textasciitilde{}275\ µs} El rendimiento de firma y validación
se mantiene muy por debajo del milisegundo a pesar de usar algoritmos
post-cuánticos ML-DSA de alto nivel de seguridad.
