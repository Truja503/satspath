\textbf{Identity \& signed profiles} & Human alias → secp256k1
public-key identity; list of payment methods; ECDSA signature over
canonical JSON; 8-char fingerprint; optional expiry & ✅ Stable \\
\textbf{Payment methods} & Lightning (Lightning Address / LNURL /
BOLT12), On-chain (multiple addresses, network-aware), Ark (server +
pubkey pointer) & ✅ Stable model --- Lightning does a real
LNURL→invoice fetch; Ark is preview-only \\
\textbf{Routing engine} & Rule-based: Lightning if amount \textless{}
100k sats → On-chain if next-block fee ≤ 20 sat/vB → Ark → else no
route; live mempool fees with safe fallback & ✅ Stable (a 2nd
score-based engine exists but is not wired in) \\
\textbf{Registry \& resolver chain} & Local file registry, then BIP-353,
then HTTP well-known, then Nostr; trust is on the signature, not the
server & ✅ Stable \\
\textbf{BIP-353 DNS payment instructions} & Resolve
\texttt{₿user@domain} to a DNSSEC-signed \texttt{bitcoin:} URI; can also
publish instructions; DNSSEC mandatory, fails closed & 🆕 New ---
resolver/preview only (never pays, signs, or broadcasts) \\
\textbf{Universal URI \& QR} &
\texttt{satspath:\textless{}alias\textgreater{}} and
\texttt{satspath:v1:\textless{}payload\textgreater{}}; BIP-21
\texttt{bitcoin:}, \texttt{lightning:}, and Ark pointers; payloads
screened for private data & ✅ Stable \\
\textbf{Ownership proofs (verification)} & Per-method proof with three
trust tiers --- cryptographic (key signature), domain-control
(well-known / Lightning-Address), self-asserted; bound to identity +
method, re-checked at resolve time & ✅ Done --- richer than a minimal
MVP needs \\
\textbf{Unregistered-user invite / claim} & Non-custodial by design: the
sender never creates the receiver's keys; invite carries alias-hash,
amount, expiry, warning & ✅ Done (invite side); claim is the receiver's
own flow \\
\textbf{UX quote JSON contract} &
\texttt{quote(recipient,\ amount\_sats)} → one JSON the UI renders by
\texttt{status} (ok / not\_registered / no\_route / invalid\_signature);
\texttt{PaymentMethod} embedded unchanged; CLI \texttt{quote\ -\/-json}
& ✅ Done (PR \#25) --- ⚠️ a second, richer shape now also exists (see
note 1) \\
\textbf{Mainnet preview mode (v2)} & Resolves, routes, and builds a
payment payload under mainnet rules; adds an execution \texttt{mode},
ownership tier, and \texttt{warnings} & 🆕 New --- preview only, no
funds move and nothing is broadcast \\
\textbf{P2P profile transfer} & \texttt{export} a signed profile as
JSON; \texttt{import} from file / stdin / HTTPS URL with signature +
expiry checks (rejects tampered profiles) & 🆕 New (offline transfer
works); networked P2P (\texttt{holepunch} SDK) is 🚧 WIP, not merged \\
\textbf{Swap engine (Boltz) + ark-bridge} & Submarine / reverse / chain
swaps; Node.js Ark bridge sidecar & 🧪 Experimental --- testnet only,
behind explicit flags \\
\textbf{CLI} &
\texttt{init,\ register,\ show,\ encode,\ decode,\ quote,\ pay,\ invite,\ demo,\ dns,\ peer,\ preview}
& ✅ Done --- primary interface today (human text + ASCII QR; JSON on
\texttt{quote}/\texttt{preview}) \\
\textbf{Safety posture} & Preview-only everywhere: no real send, no
spend-signing, no broadcast; private-material screening; output masking
by default & ✅ Enforced across the codebase \\
\end{longtable}

\hypertarget{notes}{%
\subsection{Notes}\label{notes}}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Two quote response shapes now exist} --- worth a decision
  before building the UI:

  \begin{itemize}
  \tightlist
  \item
    \texttt{quote\ -\/-json} (router, PR \#25): embeds the raw
    \texttt{PaymentMethod}; four-state enum; the shape our contract docs
    describe.
  \item
    \texttt{preview} command (mainnet preview v2): a richer JSON with a
    \textbf{reshaped} method plus \texttt{mode},
    per-recipient/per-method \textbf{ownership} tier, and a
    \textbf{warnings} list; all fields optional. These overlap but are
    not identical. The UX should target one of them (the
    \texttt{preview} shape is the newer, richer one).
  \end{itemize}
\item
  \textbf{Scope.} The must-have MVP core --- identity, signed profiles,
  signing/verification, routing, invite flow, and the quote JSON --- is
  \textbf{complete and stable}. Several areas (ownership proofs, BIP-353
  DNS, mainnet preview, P2P transfer, swaps) go \textbf{beyond a minimal
  MVP}: ambitious, but the UX-facing core is stable.
\item
  \textbf{Nothing executes real payments.} By design this is a
  signed-profile \emph{resolver + router + preview}; real send/broadcast
  is intentionally out of scope for now.
\end{enumerate}
